# Field Brain — Playbook

## 최신 결정 — 2026-09-21: 개인 실사용 우선

2026-09-22: 일정 확인 뒤 기록 메뉴로 이동해 현장을 다시 찾는 단절을 줄였다. 같은 현장 ID로 일지와 비용 확인에 이어지고, 방문은 방문 결과와 구분한다. 검증은 링크 존재만이 아니라 실제 업로드부터 자유 기록 저장과 비용 원장까지 이어지는 허구 시나리오로 수행한다. 일정의 업체금액과 작업일지의 실제 지출을 혼동하지 않는 것을 통과 조건에 포함한다.

향후 수개월은 사용자 혼자 사용한다. 공동 수정·권한 조직화·초대 기능은 당장 개발하지 않는다. 외부 접속 요구를 공동 사용 요구로 추정하지 않는다. 제공된 이메일의 소유자를 단정하지 않는다. 아래 공동 사용 구상은 보류된 이력이다.

현장 화면에서 기록을 시작할 때 이름을 다시 입력하게 하는 것은 이미 가진 맥락을 버리는 일이다. 현장 ID를 그대로 전달하고 서버에서 소유 범위를 확인한다. 이름이 같은 현장을 첫 번째 검색 결과로 선택하지 않는다. 자동 연결은 사용자 선택의 연속이어야 하며 추측으로 다른 현장 원장을 섞지 않는다.

## 방향 정정 — 2026-09-21: 외부 접속은 전체 공개가 아니다

사용자가 외부에서 앱을 보려는 목적은 지정된 업무 동료와 실제로 활용하기 위함이다. 익명 시연판은 이 요구의 완료가 아니다. 기존 공개 시연판은 소유자 한 명만 허용하는 접근으로 제한했다. 소스 공개 동의를 업무 데이터의 공개 동의로 확대하지 않는다.

앞으로 한 업무 원장, 초대 기반 접근, 휴대폰 사용을 배포 기준으로 삼는다. 편집할 때마다 별도 시연용 데이터를 복사하는 구조를 최종 제품으로 확장하지 않는다. 동료의 이메일과 보기/수정 필요 여부, 실제 데이터를 보관할 환경이 결정되기 전 임의로 사람을 초대하거나 새 외부 저장소에 원본을 전송하지 않는다.

사이트의 외부 방문 권한은 앱 안의 수정 권한과 다르다. 사이트 소스 편집자로 초대하는 것으로 현장 기록 수정 기능을 대신하지 않는다. 원본과 수정 이력, 접근 회수까지 포함한 실제 공동 사용 경로를 검증한다.

## 설계 기록 — 2026-09-16

일정 변경을 연결하기 전에 원문 날짜·시간 자체의 정확도를 점검했다. 동일 월의 생략된 종료일과 '반', 다음 주의 기준은 작은 표현 차이지만 실제 동선을 바꾼다. 해석할 수 없는 날짜를 임의 보정하지 않고 원본에 남긴다. 후속 메시지 연결은 별도 검증 대상으로 유지한다.

확정 방문에 현장 ID가 없어 수주 경로가 막히던 문제를 연결 단계에서 해결했다. 이름·주소·범위가 모두 일치하는 단일 진행 현장만 재사용한다. 표현이 다른 동일 현장은 별개로 남을 수 있으나, 자동으로 다른 공사를 병합하는 것보다 복구하기 쉽다. 현장 생성과 방문 연결은 한 트랜잭션으로 저장한다. 현재 실제 자료의 일괄 재처리는 하지 않고 다음 가져오기와 재가져오기에서 적용한다.

카톡은 일정과 확인된 견적금액을 우선하고, 실제 지출은 일지에서 수집한다는 사용자 지침을 적용한다. '업체 실행비'라는 단어만으로 비용 계정에 넣지 않는다. 공사 픽스의 금액 문구는 조건을 보존한 채 일정에 연결하고, 재수입 보완의 출처와 수정 이력을 남긴다. 숫자 하나로 강제 변환하거나 추가·부분·단가 금액을 합산하지 않는다.

자료 제출은 사용자가 가진 자료 하나에서 시작해야 한다. 카톡과 정리 문서를 둘 다 요구하면 자료를 전달하기 전에 별도 정리 작업을 시키는 셈이다. 따라서 한 자료 입력을 허용하고, 두 자료가 있으면 함께 참고하도록 바꿨다. 추출에 실패한 내용을 '일정 없음'으로 표현하지 않는다. 문서에서 읽은 일정의 근거를 카톡 원문으로 잘못 연결하지 않는다.

수주 연결은 기존 방문의 현장 ID와 내용을 재사용한다. 재입력은 최종 합의금액과 새 작업 시작에 한정한다. 수주금액·일정·현장 상태는 하나의 저장 단위로 다뤄 부분 성공을 막는다. 같은 소식 재전송과 금액 수정도 별도로 검증한다. 넓은 문맥 해석을 하는 척하지 않기 위해 현재 지원 형식과 한계를 입력창에 명시한다. 추후 모델 기반 추출도 이 저장 경계와 중복·이력 규칙을 통과해야 한다.

방문 결과가 일정 상세에 갇혀 현장에서 재사용되지 않던 연결을 먼저 개선했다. 자유 메모를 기본으로, 구조화된 세부 입력은 선택으로 유지한다. 원본 의미를 강제 분해하지 않으며 기존 필드를 숨긴다는 이유로 삭제하지 않는다. 같은 현장 ID에 연결된 결과만 보여 주어 다른 현장의 견적이 섞이지 않게 한다. 제안 견적은 수주와 다르므로 장부에 복제하지 않는다.

## 0. 큰 그림 우선 운영 원칙 — 2026-09-10

이 절은 현재 Playbook의 최우선 기준이다. 종전의 전체 결과 검토·승인 중심 루프는 이 절로 대체하고, 과거 본문은 연구 이력으로 유지한다. 실제 화면·기능·개발 순서는 [Product](PRODUCT.md)의 0절을 따른다.

### 이번에 방향을 바로잡는 이유

사용자는 기능이 없는 것만 문제 삼지 않았다. 자료를 전달했는데 다시 입력해야 하는 것, 모든 결과를 검토하게 하는 것, 화면을 열어도 무엇을 해야 할지 모르는 것에 반복적으로 불편을 말했다. 그런데 개발은 인건비 계산·항목 분류·브리핑 문구 같은 부분을 완성하는 데 집중했다.

문제의 원인은 기능 연결을 확인하는 대표 업무 시나리오 없이 작은 요청을 각각 구현한 것이다. Product에 사용 흐름을 적어 두었지만 실제 다음 작업 선택을 통제하지 못했다. 앞으로 완료 단위는 버튼이나 카드가 아니라 '자료 하나가 현장 판단으로 연결되는 흐름'이다.

### 유지할 제품 철학과 사용자 결정

Field Brain은 사용자의 업무를 기억하고 함께 성장하는 AI다. 첫 사용자 황태환의 철거 사업 성공을 우선한다. 범용 플랫폼의 가능성은 실제로 도움이 된 방식에서 얻는다.

- 일지는 자유롭게 쓴다. 참고 목록이 입력 의무가 되어서는 안 된다.
- 카톡 자료 전달과 개인 작업일지는 서로 다른 입력 의도를 유지한다.
- 방문 일정과 작업 일정은 다른 업무다. 일정 겹침은 정상일 수 있다.
- 확실한 일정은 바로 보이고, 맞는 결과를 유지하려고 승인 버튼을 누를 필요가 없어야 한다.
- 견적 방문 담당자·방문 상태 선택, 미수금 추적, 중개수수료는 현 범위에서 제외한다.
- 지출을 중심으로 보되, 수주 안 된 견적은 수익 계산의 매출로 취급하지 않는다.
- 현장 참고에는 용어·단가·사례를 남긴다. 사용자가 제외한 요령을 자동으로 다시 채우지 않는다. 사용자가 직접 복원한 항목은 존중한다.
- 인건비 세부 개선은 지금 하지 않는다. 이미 만든 기능은 전체 흐름을 깨지 않는 범위에서 유지한다.

### AI와 사용자의 역할

사용자는 경험과 자료를 전달하고 필요한 사업 결정을 한다. 앱은 자료를 연결하고 계산하고 정리하며, AI는 그 자료의 의미·변화·누락 가능성을 설명한다. 계약 수락, 고객 연락, 금액 청구처럼 실제 외부 행동을 모델이 임의로 실행하지 않는다.

원하는 기본 흐름:
자료 전달 → 업무 기억 갱신 → 현재 상황과 다음 행동 확인 → 틀린 부분만 수정 → 다음 처리와 견적에 재사용.

사용자가 적은 '일했다'와 앱이 추정한 '비용 지급 완료'를 같게 취급하지 않는다. 원본·사실·해석·사용자 결정을 내부에서는 구분하지만, 그 관리 부담을 기본 화면에 모두 드러내지 않는다.

### 첫 실사용 관찰과 성공 기준

대표 현장 하나를 문의부터 완료까지 따라간다. 처음에는 허구 시나리오로 검증하고, 연결이 확인되면 사용자가 이미 제공한 실제 자료에 적용한다. 과거 모든 금액을 정확히 다시 입력하도록 요청하지 않는다. 한 판단에 꼭 필요한 자료가 빠졌을 때에만 어떤 내용이 왜 필요한지 구체적으로 묻는다.

관찰할 것:
- 같은 현장·일정·비용을 사용자가 두 번 입력했는가?
- 다음 날 앱을 열었을 때 일정과 현장 상태가 이어졌는가?
- 수주 안 된 금액, 다른 현장 비용, 예상 비용이 결과를 왜곡했는가?
- 사용자가 오늘 행동을 결정하기 위해 원문 전체를 다시 읽어야 했는가?
- 다음 견적에서 실제로 도움이 된 과거 자료가 있었는가?

목표는 일정 확인 30초, 현장 상황 파악 1분, 정상 결과 승인 클릭 0회, 동일 내용 재입력 0회다. 측정 전에는 달성했다고 보고하지 않는다. 미확인 항목을 전부 질문 목록으로 만드는 것도 실패다.

### 온보딩·자료·권한 연구

최초 질문은 주 업무, 현재 일감을 받는 방식, 자료가 생기는 경로, 지금 놓치기 쉬운 판단으로 제한한다. 작업자 전원의 일당이나 모든 과거 견적을 초기 사용의 조건으로 요구하지 않는다.

처음 요청할 자료는 최근 현장 한 건의 일정 대화와 짧은 작업일지다. 로컬 파일 선택부터 시작한다. 전체 카톡·연락처·사진 접근 권한은 기본 요구하지 않는다. 통화·사진 해석이나 외부 모델 전송을 연결할 때 목적·전송 범위·보존 방식을 설명한다. 이 문서 작성으로 새 외부 전송 권한을 얻은 것은 아니다.

### 축적할 데이터를 구분한다

1. 철거 업무 데이터: 개인·고객·주소·가격·대화·사진·원문 근거. 로컬 실제 업무 원장.
2. 사용자 행동/수정 데이터: 무엇이 틀렸고 어떻게 고쳤는지, 반복 입력과 이탈. 필요한 범위만 로컬에 남기며 새 분석 수집은 별도 설계.
3. Field Brain 공통 설계 데이터: 익명화된 문제 유형, 연결 원칙, 실패 사례의 구조. 실제 개인정보나 업체별 단가를 그대로 복사하지 않는다.

업무팩 후보는 용어·범위 종류·문서 패턴·비용 분류다. 두 번째 업종을 추가하기 전에는 철거의 실제 흐름이 통과해야 한다. 외부 코드·자료 재사용 시 라이선스와 출처를 확인하고, 참고 기록을 제품 공통 콘텐츠로 자동 공개하지 않는다.

### 자료 전달 직후 결과를 보여주는 원칙 (2026-09-21)

업로드 성공 건수만 보여주면 사용자는 어떤 일정이 어디로 갔는지 알 수 없다. 특히 과거 자료는 현재 달 달력에 나타나지 않아 실패로 느낀다. 따라서 이번 자료가 연결한 일정 자체를 종류별로 보여주고 현장으로 이어준다. 재업로드한 기존 일정도 제외하지 않는다. 취소된 일정을 새 예정으로 표현하지 않도록 저장 후 최신 상태를 읽는다. 모든 행에 재승인을 요구하는 단계는 추가하지 않는다.

### 다음 작업을 선택하는 규칙

매 작업 시작 시 Product 0절의 어느 연결을 완성하는지 먼저 적는다. 해당 연결의 입력 예와 사용자가 보게 될 결과를 정한 뒤 구현한다. 끝날 때는 구현 범위·실제로 검증한 경로·남은 끊김을 분리해 보고한다.

독립 기능 요청이 오더라도 전체 흐름에 어디에 연결되는지 먼저 정한다. 연결이 없는 세부 기능은 보류 목록에 기록한다. 작은 테스트가 통과했다는 이유로 바로 다음 디테일로 넘어가지 않는다.

이번 결정에서 앱 코드는 바꾸지 않았다. Product와 Playbook의 큰 그림 및 실행 순서를 기준으로 다음 구현을 진행한다.
